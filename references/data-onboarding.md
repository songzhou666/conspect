# 数据接入：任意行业、任意表格怎么进得来

> 这份文档回答一个问题：**用户丢过来一张千奇百怪的表，流程靠什么不出错？**
> 答案不是"关键词写得够多"，而是**分层**——把「看数据」「判语义」「算数字」拆给不同的层，
> 每层只做它做得了的事，做不了的显式交出去。

---

## 一、先回答三个常见误解

| 误解 | 事实 |
|------|------|
| "AI 会自动理解我的数据" | 不完全。AI 只负责**判语义**（这列是什么角色），看数据与算数字都是确定性代码 |
| "工具按固定格式解析，格式不对就报错" | 不对。格式兼容由探测层处理（中文日期、混合类型、千分位都吃得下），不走固定 schema |
| "流程是直接对着原始表拆分提炼" | 不是。**必须先建立数据契约，再按契约计算**——否则同一张表每次跑出来的结论都可能不同 |

---

## 二、四层架构（为什么必须分层）

```
┌─────────────────────────────────────────────────────────────┐
│ D 探测层  schema_probe.py                                    │
│   只看数据本身，产出可复算的统计事实                          │
│   例：unique=940、null_rate=0、date_rate=1.0、avg_len=6.9     │
│   不做业务判断 · 不看列名含义                                 │
├─────────────────────────────────────────────────────────────┤
│ S 判定层  schema_probe.judge_by_stats + AI                     │
│   硬证据 → 直接定（日期、全空、全唯一大整数、低基数枚举）      │
│   模糊地带 → 标 low / unknown，交 AI 或人                     │
│   允许说"不知道"，这是设计而非缺陷                            │
├─────────────────────────────────────────────────────────────┤
│ C 契约层  schema_contract.py                                  │
│   判定结果落成 _cs-schema.json，全链路只读它                    │
│   判定只发生一次 → 不会出现"三个模块各判一套"                  │
│   数据契约是判定的唯一事实源                                  │
├─────────────────────────────────────────────────────────────┤
│ E 计算层  data_processor / chart_advisor / render_engine       │
│   按契约算：聚合方式、能不能出图、算不算维度                   │
│   不再自行猜测（关键词表只作无契约时的兜底）                   │
└─────────────────────────────────────────────────────────────┘
```

**为什么早期版本会"每来一张新表就要调"**：
判定散落在三个模块里——`identify_dimensions` 按 dtype 判、`chart_advisor` 用
`NON_METRIC_HINTS` 黑名单再拦一次、`ai_agent._features_from_analysis` 又过滤一次。
每遇到一个新行业的新术语（客单价、GMV、到店人次、POI 数），就要在三处同时补关键词，
漏一处就出错。**分层之后，新行业只需在 S 层判一次，D 层与 E 层完全不动。**

## 三、角色体系（契约的核心）

每列被判为七种角色之一：

| role | 含义 | 下游能做什么 | 典型误判后果 |
|------|------|-------------|-------------|
| `time` | 时间轴 | 趋势、时间序列聚合 | 时间点没识别 → 报表里没有趋势图 |
| `dimension` | 分组维度 | 分类聚合、排名、构成 | 高基数名称当维度 → 饼图出几百个扇区 |
| `measure` | 度量 | 求和/均值（受可加总性约束） | 电话当度量 → "平均联系方式" 这种荒谬指标 |
| `identifier` | 标识/明细ID | **只能计数** | 订单号当维度 → 排名图变成明细表 |
| `text` | 自由文本 | 不参与数值分析 | 备注列进图表 → 无意义 |
| `ignore` | 全空/常量 | 完全不参与 | 常数列占满图表 |
| `unknown` | 未判定 | **不参与分析，但必须明示** | 静默归入分类 → 错误结论无人察觉 |

### 可加总性（只有 measure 需要）

| additivity | 含义 | 求和会怎样 |
|-----------|------|-----------|
| `additive` | 求和有意义 | 正确（销量、金额、订单数） |
| `average` | 求和无意义 | 荒谬（单价相加 = 天文数字） |
| `none` | 非度量 | — |

**这一项必须由 AI 或人判，统计判不出来。** 实测依据：GMV 与客单价都是正小数、
都右偏分布，统计特征几乎一样，但前者求和有意义、后者毫无意义。
用 22 个真实度量列测试，纯统计只能判对 9 个（40.9%）——所以探测层对判不出的
一律返回 `hint`，契约落为 `average`（安全侧）并标记 `additivity_confirmed: false`，
报表口径必须声明「该指标可加总性未确认，已按均值处理」。

## 四、标准流程（三个阶段）

### 阶段 1：探测（不写盘，只看证据）

```powershell
'{"file_paths": ["E:/data/任意行业表.xlsx"]}' | python run.py probe_schema
```

返回每列的完整画像与**待判清单**：

```json
{
  "columns": [
    {"column": "就诊人次", "role": "measure", "confidence": "high",
     "evidence": "hard", "reason": "数值型，作度量（可加总性需由契约确认）",
     "additivity": "additive", "unique": 3, "null_rate": 0, "samples": ["1","2","3"]},
    {"column": "诊所名称", "role": "dimension", "confidence": "low",
     "evidence": "weak", "reason": "大基数分类（940 类，占比 38%），需确认业务含义"}
  ],
  "summary": {"total": 29, "high": 25, "medium": 1, "low": 3, "unknown": 0},
  "need_ai": ["诊所名称", "市", "区"],
  "unresolved": [],
  "duplicate_columns": [["填写人", "填写人(人员)"]],
  "ready": true
}
```

**看三个字段就够了**：
- `need_ai` —— 必须你（或 AI）拍的列。8 个行业实测平均只有 **0–5 列**，不是几十列。
- `unresolved` —— 统计层完全判不出的列。若确实无用，可留 `unknown`（不参与分析但要明示）。
- `duplicate_columns` —— 内容完全相同的列，容易在报表里被算两遍。

### 阶段 2：固化契约（判定只做一次）

```powershell
'{"file_paths": ["E:/data/任意行业表.xlsx"],
  "overrides": {
    "诊所名称": {"role": "dimension", "reason": "诊所是分组单位，用于覆盖度分析"},
    "市":       {"role": "dimension", "reason": "城市层级，可做区域下钻"}
  },
  "decided_by": "ai"}' | python run.py save_schema
```

`overrides` 只需给 `role`；`additivity` 可省略（自动按统计特征推断，
判不出则落 `average` 并标未确认）。产出 `_cs-schema.json`。

**这张契约就是"标准数据表"** —— 它不改动原数据，只把"每列是什么"固定下来。
同一份契约重复跑 analyze，结论必然一致。

### 阶段 3：按契约分析

```powershell
'{"file_paths": ["E:/data/任意行业表.xlsx"],
  "schema_file": "E:/proj/.agent/harness/_cs-schema.json"}' | python run.py analyze
```

`analyze` 返回的 `dimensions._provenance` 会说明来源：

| source | 含义 | 是否可作正式报表 |
|--------|------|-----------------|
| `contract` | 用了你提供/确认过的契约 | 是 |
| `auto_contract` | 没给契约，现场统计探测生成 | 可出初稿，口径须声明未经复核 |

### 换了新版数据怎么办

```powershell
'{"file_paths": ["E:/data/新版.xlsx"], "schema_file": "旧的 _cs-schema.json"}' | python run.py check_schema
```

返回新增列、缺失列、非法 role。**新增列不会被静默塞进分类**，
而是标为 `unknown` 并在 `data_issues` 里报「角色未判定」。

## 五、兜底链（用户什么都不给时会怎样）

```
用户给了可用契约       → 严格按契约执行（source=contract）
用户没给契约           → 现场探测生成契约（auto_contract），
                         need_ai 列在 note 里列出，口径声明"未经复核"
探测失败（文件坏等）    → 报错并中止，不产出猜测性结论
某列判定为 unknown     → 该列不参与分析，并在 B19 数据质量说明板块明示
```

**没有"静默用关键词猜"这条路径。** 关键词表只在 `auto_contract` 的统计启发式里
作为弱线索参与，且输出必带 `evidence: "weak"` 与 `confidence: medium/low`。

## 六、能力边界（诚实清单）

### 探测层做得到的（硬证据，不看列名）

| 判断 | 判据 | 实测 |
|------|------|------|
| 时间列 | 日期可解析率 ≥90%（含中文「2025年06月27日」） | 100% |
| 全空 / 常量 | unique=0 / unique=1 | 100% |
| 电话、证件号 | 全唯一 + 整数 + ≥8 位 | 100% |
| 地址、链接、文件名 | 全唯一 + 平均 ≥20 字 | 100% |
| 枚举维度 | 2–30 类且占比 <5% | 100% |
| 数值即度量 | dtype 是数字 | 100% |

8 个行业 59 个关键列，**纯统计 role 准确率 100%**。

### 探测层做不到的（必须交契约）

| 场景 | 为什么判不出 | 处理 |
|------|-------------|------|
| GMV vs 客单价 | 都是正小数右偏分布 | 返回 `hint`，契约判 |
| 「客户名称」是维度还是明细ID | 48 类、占比 67%，统计无区分度 | 标 `low`，交 AI |
| 「诊所名称」940 类 | 既是分组单位又接近逐行唯一 | 标 `low`，交 AI |
| 小数金额能否求和 | 无统计特征可依 | 返回 `hint` |

**这不是缺陷，是能力边界的诚实标注。** 假装判得出，就会输出错误报表。

### 实测数据（8 行业 / 59 关键列 / 22 度量列）

| 路径 | role 准确率 | additivity 准确率 | AI 需看的列 |
|------|-----------|------------------|-----------|
| 纯自动（无干预） | **100%** | 40.9%（其余 59% 标 hint） | — |
| AI 终判后 | **100%** | **100%** | 平均 2.75 列（0–5） |

行业覆盖：零售电商（GMV/客单价）、医疗门诊（ICD/身份证）、物流运输（里程/体积重）、
教育培训（课时/出勤率）、制造业（不良率/单件成本）、脏数据混合（中文日期/千分位/全角空格）、
宽表稀疏（120 列 90% 缺失）、小样本（18 行）。

## 七、给新行业的操作建议

1. **先跑 `probe_schema`**，看 `need_ai` 有几列。
2. **只判那几列**，别整表通读——实测平均不到 3 列。
3. **重点判 `additivity`**：哪个能求和、哪个只能取均值，这直接决定报表里的数字对不对。
4. **跑 `check_schema`** 确认契约与实际表匹配。
5. 数据换版本后**先 `check_schema` 再 analyze**，避免用旧契约套新数据。

> 一句话：**不要期待 AI 认识你的行业术语，而是把术语到角色的映射建立一次、固化下来。
> 建一次的成本是判 3 列，之后同行业同格式的表都能直接跑。**
